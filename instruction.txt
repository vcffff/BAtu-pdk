# Task: generate a Packet Tracer lab as a real .pkt (NAT-PT, IPv6 islands over an IPv4 core)

## Context: this repository
This repo (packet-tracer-pkt-format) reverse-engineers the .pkt container and ships a Python authoring API, `pkt_core.builder.Lab`. It writes devices, cabling, IOS config (as RUNNINGCONFIG lines) and PC IPs straight to a file Packet Tracer opens, without Packet Tracer installed. Use it. Do NOT use PTBuilder/JavaScript and do NOT hand-roll the encryption.

## Read first, before writing any code
1. `SKILL.md` (the packaged agent skill). Obey all of its rules. Rules 7 and 8 (cables, and port names that make PT refuse the whole file with a generic "not compatible" error) are critical.
2. `docs/CONFIGURATION.md`, `docs/CAPABILITIES.md`, `BUILDER_PORT.md`, `docs/SCENE_GRAPH.md`.
3. `demo/build_demo.py` (worked example) and `tools/lab_api.py` / `src/pkt_core/builder` for the real signatures. Use the actual API, not the README snippet from memory. If this checkout differs from the README, the code wins.
Install in editable mode or `pip install packet-tracer-pkt-format` (Python 3.10+).

## Hard constraints
- Do not claim the file was opened or tested in Packet Tracer. You cannot run it. Verification is limited to what the repo tooling can check (see "Verification"). At the end, list what you are unsure about.
- Verified by the user in real PT: ISR4331 accepts `ipv6 nat ?` (prefix, v4v6, v6v4) and REJECTS `nat64`. Use NAT-PT only. No `nat64` command anywhere.
- Interface names: ISR4331 = GigabitEthernet0/0/0, 0/0/1, 0/0/2. Cisco 2911 = GigabitEthernet0/0, 0/1, 0/2. Switch 2960-24TT = FastEthernet0/1.. . End devices use FastEthernet0.
- Every port used in a link must exist on that exact device instance in the template/model you add. Check this programmatically before saving. Do not guess port names. If a model is not in the bundled template library, stop and report it. Do not substitute silently.
- Do not set console, enable or VTY passwords in any config.
- Do not use `tools/make_scored_lab.py` or the .pka/scoring tooling. This is a plain .pkt, not an activity.
- Do not use the "answer key / assessment" parts of this repo for anything. Not relevant here.

## Deliverables (create in ./pt_lab/)
1. `build_lab.py`: builds the lab with `pkt_core.builder.Lab` and writes `NAT64_lab.pkt` (output path as a CLI arg, default `./pt_lab/NAT64_lab.pkt`). Steps: `Lab()`, `prune_seed_devices()`, `add_device(...)` for every device at the coordinates below, `link(...)` for every link, IOS config for each router read from `configs/<DEVICE>.txt`, IPv4 settings for IPv4 hosts via `pc_ip=(ip, mask, gateway)` (add DNS only if the API supports it). Prefer the API's own cable handling (auto cable type); if you must pick explicitly, use straight-through for router/switch and switch/host, crossover for router-to-router.
2. `configs/<DEVICE>.txt`: one plain paste-ready CLI file per router (NAT1, NAT2, NAT3, C1, C2, C3, C4), starting with `enable` and `configure terminal` and ending with `end` and `write memory`. No leading indentation. These are the single source of truth: `build_lab.py` loads them (check how the builder wants config lines: with or without `enable`/`configure terminal`/`write memory`, and with indentation or not, and strip or adapt accordingly while keeping the .txt files paste-ready).
3. `verify_lab.py`: re-opens the generated .pkt and runs the checks in "Verification".
4. `README.md`: how to build (`pip install`, run `build_lab.py`), how to open in PT, the manual steps, the test plan, and the uncertainties list.

## NAT router template (NAT1, NAT2, NAT3; replace {N}, {POOL_START}, {POOL_END})
```
enable
configure terminal
hostname NAT{N}
ipv6 unicast-routing
interface GigabitEthernet0/0/0
ipv6 address 2001:db8:{N}::1/64
ipv6 enable
ipv6 nat
no shutdown
exit
interface GigabitEthernet0/0/1
ip address 10.0.{N}.2 255.255.255.252
ipv6 nat
no shutdown
exit
ip route 0.0.0.0 0.0.0.0 10.0.{N}.1
ipv6 access-list V6HOSTS
permit ipv6 2001:db8:{N}::/64 any
exit
ipv6 nat prefix 2001:db8:64::/96
ipv6 nat v6v4 pool P{N} {POOL_START} {POOL_END} prefix-length 28
ipv6 nat v6v4 source list V6HOSTS pool P{N}
```
Then append the tunnel block (tunnel interfaces must NOT have `ipv6 nat`):
- NAT1: Tunnel12 (ipv6 2001:db8:12::1/64, source 10.0.1.2, destination 10.0.2.2, mode ipv6ip), Tunnel13 (2001:db8:13::1/64, source 10.0.1.2, destination 10.0.3.2); `ipv6 route 2001:db8:2::/64 2001:db8:12::2`; `ipv6 route 2001:db8:3::/64 2001:db8:13::2`
- NAT2: Tunnel12 (2001:db8:12::2/64, source 10.0.2.2, destination 10.0.1.2), Tunnel23 (2001:db8:23::1/64, source 10.0.2.2, destination 10.0.3.2); `ipv6 route 2001:db8:1::/64 2001:db8:12::1`; `ipv6 route 2001:db8:3::/64 2001:db8:23::2`
- NAT3: Tunnel13 (2001:db8:13::2/64, source 10.0.3.2, destination 10.0.1.2), Tunnel23 (2001:db8:23::2/64, source 10.0.3.2, destination 10.0.2.2); `ipv6 route 2001:db8:1::/64 2001:db8:13::1`; `ipv6 route 2001:db8:2::/64 2001:db8:23::1`
Keep the tunnel config in a separate, clearly marked section of each config file, and make `build_lab.py` able to omit it (`--no-tunnels`), because `tunnel mode ipv6ip` may be rejected by some PT versions (alternatives to document: `tunnel mode gre ipv6`, `tunnel mode gre ip`).

## Verification (what you CAN check offline; run it and report real output)
In `verify_lab.py`, using `pkt_core`:
1. `pkt info` on the output: container decodes, root tag `PACKETTRACER5`.
2. Round trip: `encode(decode(f)) == f` byte-exact.
3. Load with `Lab.from_bytes(decode(f).xml)`: expect 17+4... count the devices (7 routers + 4 switches + 6 hosts + 3 servers/legacy = 20 total; recompute from the tables) and 25 links; print any mismatch.
4. For every link: both ports exist on their device, no port used twice, link endpoints match the Links table exactly.
5. Each router's stored running config contains the expected key lines (hostname, `ipv6 nat v6v4`, tunnel block present/absent, OSPF).
6. `pkt unpack` to a temp dir and confirm per-device IOS configs match `configs/*.txt` after normalisation.
7. `pkt audit` on the file. Report the result. Template leftovers (stale hostnames, phantom IPs, duplicated DHCP pools or AAA clients inherited from harvested templates) must be cleaned if audit flags them.
8. Check that no device still carries a template's factory/stale config and that device names are unique.
State plainly that passing these does NOT prove Packet Tracer will open the file or accept every command.
